# Business Entity Resolution: Phase 3 Feature Engineering Documentation

## 1. Overview & Architectural Principles

Phase 3 introduces a high-throughput, leakage-free pairwise feature extraction pipeline designed to transform candidate pairs generated by the Phase 2 v2 hybrid blocker into dense numeric feature vectors for downstream machine learning classifiers (LightGBM / XGBoost / CatBoost).

### Key Design Pillars:
1. **100% Numeric Representation**: All 69 features are strictly floating-point values (`np.float32`). No categorical string columns or complex objects are emitted, eliminating preprocessing overhead during model training and inference.
2. **Robust Handling of Messy & Missing Data**:
   - Missing addresses, unparsed strings, and empty fields are gracefully captured via explicit binary indicators (`addr_s1_missing`, `addr_both_missing`, etc.) rather than generating `NaN` or `Inf`.
   - Feature arrays are guaranteed to contain **zero NaNs and zero infinite values**.
3. **Dual Representation (Normalized vs. Raw Suffixes)**:
   - Standard business name normalization strips legal entity suffixes ("LLC", "Corp", "Private Limited"). However, OCR errors or misspellings in the suffix (e.g. "Enterpires" vs "Enterprises") can cause asymmetric stripping.
   - The extractor computes similarities across **both** normalized name cores and cleaned raw strings, ensuring typos in entity types do not penalize matching scores.
4. **Multi-Channel Evidence Propagation**:
   - Rather than discarding the candidate generator's scoring signals, the feature extractor incorporates candidate rank, reciprocal rank, composite blocking score, score ratio to top candidate, and individual blocking channel activations.
5. **Strict Data Leakage Prevention**:
   - Ground-truth match labels (`is_match`) are strictly isolated as target outcome labels and never touch feature calculations.
   - Feature computations are purely pairwise and stateless.

## 3. Data Leakage Prevention Architecture

Data leakage is a common pathology in entity resolution when candidate statistics, cluster sizes, or target labels contaminate feature values:
1. **Target Isolation**:
   - The match indicator `is_match` (0/1) is added exclusively as an independent supervision column when formatting training DataFrames.
   - It is never fed into any normalization routine, token vocabulary, IDF calculation, or pairwise similarity function.
2. **Stateless Extractor Design**:
   - `extract_pair_features()` is a pure, idempotent function operating only on the attribute strings of the two entities being compared and query-local blocking metadata.
3. **Partition Invariance**:
   - Features extracted on training splits, validation splits, or unseen test splits use the identical calculation logic with no target-dependent state.

## 5. Usage Example (Downstream ML Handover)

```python
from business_entity_resolution.blocking.candidate_generator import CandidateGenerator, STRATEGY_COMBINED_HYBRID
from business_entity_resolution.features.pair_features import PairFeatureExtractor, ALL_FEATURE_NAMES

# 1. Fit Candidate Generator on Candidate Source
generator = CandidateGenerator(strategy=STRATEGY_COMBINED_HYBRID, max_candidates=100)
generator.fit(s2_candidate_records)

# 2. Build Feature Matrix for S1 Queries
extractor = PairFeatureExtractor()
df_pairs = extractor.build_candidate_pair_dataset(
    s1_queries=s1_queries,
    candidate_records=s2_candidate_records,
    candidate_generator=generator,
    target_source="S2",
    gt_map=training_ground_truth_map,  # Optional: adds 'is_match' label
    k=100,
)

# 3. Direct Input to LightGBM
X = df_pairs[ALL_FEATURE_NAMES].values
y = df_pairs["is_match"].values
```
